# CLAUDE.md — How to work in this repository

**Read this first. Then `docs/README.md`.**

This is the COS597C (Fall 2026) Project 1 of Hammad Farooqi and Vatsal Parikh. τ²-bench gives
credit to agents that do nothing: a null agent passes 23 of 50 airline tasks. We change the
benchmark so that a **no-action** verdict is graded as **justified** (the agent reasoned its way
to it) or **unjustified** (it got there by accident).

Two people, and their agents, work in this repository at the same time. The rules below keep
the documents from drifting apart. Follow them exactly.

---

## 1. Read order for a cold start

Do not read everything. Read in this order and stop when you have what you need.

1. **This file** — the rules.
2. **`docs/README.md`** — the generated map. Every document, with its date and status.
   (The root `README.md` is the hand-written guide for readers of the submission.)
3. **`docs/decisions/milestones.md`** — the master tracker. What is done, what is next, who owns it.
4. **`docs/decisions/charter.md`** — what the project is and what "done" means.
5. **`docs/decisions/decisions-log.md`** — every settled decision, newest at the bottom.
6. **`docs/research/findings-log.md`** — the evidence. Only the entries your task needs.
7. **Only then**, `code/README.md` and the code your task touches.

For background on a paper, read `docs/papers/index.md` first.

---

## 2. Which file wins when two disagree

1. `docs/decisions/decisions-log.md` — the newest entry on a subject beats everything.
2. `docs/decisions/charter.md` — authoritative on scope, goals, and the rubric.
3. `docs/decisions/milestones.md` — authoritative on status and ownership, not on scope.
4. `docs/research/` — authoritative on detail and evidence.
5. Meeting notes — a record of a moment, not a standing decision.

**Never resolve a conflict silently.** Say which documents disagree, say which one you
followed, and add an entry to the decisions log if the disagreement is now settled.

## 3. Layout

```
CLAUDE.md                  this file (not indexed)
README.md                  hand-written guide for readers: results, quick start, layout
docs/
  README.md                GENERATED by tools/build_index.py — never edit by hand
  decisions/               charter, milestones, decisions log
  research/                findings log, and research notes
  meetings/                ISO-dated meeting notes (create the folder with the first one)
  external/                what was submitted or shown (proposals, reports)
  drafts/                  written, not yet submitted (create with the first one)
  papers/                  index of the papers we cite
code/
  README.md                what each part of the code does, and how to run it
  tau2-bench/              our modified copy of sierra-research/tau2-bench
tools/build_index.py       regenerates docs/README.md and audits the docs
```

**Docs and code stay separate.** The reasoning goes in `docs/`. The code goes in `code/`.
`code/README.md` says what each file does and links to the docs for the "why".

## 4. Document types

The `type:` field in each document's frontmatter tells you how much to trust its age.

| Type | Where | Ages? |
|---|---|---|
| `charter` | `docs/decisions/` | Must be kept current. It is the spine. |
| `milestones` | `docs/decisions/` | Must be kept current. Update it in the same commit as the work. |
| `log` | `docs/decisions/`, `docs/research/` | **Append only.** Cannot go stale, because nothing is ever edited. |
| `research` | `docs/research/` | **Goes stale.** Facts about models, APIs, and libraries expire. Check `review_by`. |
| `meeting` | docs/meetings/ (create with the first note) | A fixed record. Never edit an old one. |
| `external` | `docs/external/` | What was submitted or shown. Never edit after sending. |
| `draft` | docs/drafts/ (create with the first draft) | Not yet submitted. **Expect to revise.** Promote to `external` when sent. |
| `index` | anywhere | A guide to a folder. |

## 5. Rules you must follow

### 5.1 Frontmatter on every Markdown file

Every `.md` file in `docs/` and `code/README.md` starts with this block. The index generator
skips files without it, and the audit reports them. (Files inside `code/tau2-bench/` are
upstream files and are not indexed.)

```yaml
---
title: Findings Log
type: log               # charter | milestones | research | log | meeting | external | draft | index
status: current         # current | needs-review | superseded
updated: 2026-10-03     # the date the CONTENT last changed
review_by: 2026-10-20   # optional: when the facts here expire
summary: >-
  One or two sentences. This is what shows in the docs/README.md table.
note: >-
  Optional. A caution, or what superseded this.
---
```

### 5.2 Bump `updated:` whenever you change content

If you change a document's content, change its `updated:` date in the same edit. Do **not**
bump it for a typo fix or a reformat. The audit compares `updated:` with the date of the last
git commit that touched the file, and warns when the commit is newer.

### 5.3 Keep the milestones file current

`docs/decisions/milestones.md` is the master tracker. When you start, finish, block, or drop a
milestone, change its row **in the same commit as the work**. A finished milestone links to its
evidence: a findings-log entry, a results folder, or a commit. Add new milestones when the plan
grows. Never delete a row; mark it `dropped` and say why in the decisions log.

### 5.4 Append to the decisions log when something is settled

Add an entry to `docs/decisions/decisions-log.md` whenever:

- a choice is made that changes what gets built or measured,
- a plan is contradicted by new evidence,
- an assumption in the charter is tested and found right or wrong,
- a meeting with course staff settles something.

Append only. Never edit or delete an entry. When a decision changes, add a new entry that says
what it replaces.

### 5.5 Append to the findings log when you measure something

Every experiment run that matters gets an entry in `docs/research/findings-log.md`: what was
run, the exact command or config, the results folder, the numbers, and what they mean. Write
the numbers down even when they are disappointing. Append only, newest at the bottom.

### 5.6 Sign your entries

Two people share these logs. Put the author in each new log entry and milestone change:
`**By:** Hammad` or `**By:** Vatsal` (add `+ Claude` when an agent wrote it).

### 5.7 Regenerate the index after any document change

```bash
python3 tools/build_index.py           # rewrite docs/README.md, print the audit
python3 tools/build_index.py --check   # audit only; exit 1 on warnings
```

**Never edit `docs/README.md` by hand.** Change the frontmatter in the document instead.
The root `README.md` is hand-written. Update its results table and commands when the final
numbers or the run commands change.

### 5.8 Naming

- **Folders and files:** lowercase, hyphens, no spaces.
- **Dated artifacts** (meetings, submissions, reports) get an **ISO date prefix**:
  `2026-10-02-proposal-formalization.pdf`.
- **Living documents** get **no** date in the filename. Their date lives in the frontmatter.

### 5.9 Cross-reference by full path from the repository root

Write `` `docs/research/findings-log.md` ``, not "the findings doc". The audit checks these
paths and reports the broken ones.

## 6. Experiment results

- Results go to `code/tau2-bench/data/simulations/<run-name>/`. **These are tracked in git** so
  that both of us work from the same data. Give each run a descriptive `--save-to` name, for
  example `airline_gpt41_check`, not the default timestamp.
- **Never put an API key in a command that writes it to disk.** tau2 saves `llm_args` in every
  results file. Our copy redacts any key named like `api_key`, `token`, `secret`, or
  `password`, but check a new results file before you commit it:
  `git diff --cached | grep -E 'pit_|sk-'` must print nothing.
- Keys live in a `.env` file in `code/tau2-bench/` (git-ignored). `code/tau2-bench/.env.example` lists them.

---

## 7. Working in `code/`

- `code/tau2-bench/` is a **copy** of the upstream repository, not a submodule. We edit it
  directly. Its upstream commit is in `code/README.md`.
- **Read a file before you overwrite it.**
- Run tau2 commands from `code/tau2-bench/` with `uv run`. Set up with `uv sync --extra dev`.
- Before you commit Python changes, run `make lint` and `make format` in `code/tau2-bench/`.
- When a commit implements a decision, cite its date in the commit message, for example
  `implements 2026-10-03 decision: track results in git`.
- Never commit model weights, large caches, or `.env`.

---

## 8. Writing style

Write anything technical in **ASD-STE100 Simplified Technical English**: short sentences, active
voice, one instruction per sentence. State uncertainty plainly. A document that hides its own
weak points is worse than useless on a research project.

---

## 9. Personal tooling stays out of the repository

Each person's agent may have personal instructions (for example daily logs in a private notes
vault, or `skill-observations/`). Follow them, but do not write personal paths or personal notes
into this repository. `skill-observations/` is git-ignored for that reason.
